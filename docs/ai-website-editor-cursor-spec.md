AI Website Editor Demo — Cursor 開發規格
目標：先做一個真正可操作、能持久儲存的 AI 網站編輯器 Demo。業主用自然語言修改既有網站內容與樣式，預覽後再發布。

第一階段不讓 AI 直接改寫專案原始碼。Replit / Coding Agent 的第二種方案只做技術調查與架構筆記，不實作。

0. 開發原則
1. 先檢查目前 repo、框架版本、部署方式與現有程式；不要不必要地重建專案。
2. 優先沿用現有 Next.js + Tailwind 技術棧。若 repo 為空，再建立合理的 Next.js App Router 專案。
3. 部署目標以 Cloudflare 為主。不要假設 Node.js 專用 API 能直接在 Cloudflare Workers 執行；先確認採用的 Cloudflare 部署模式與相容性。
4. 先做可運作的垂直切片，再補 UI 細節。不要只交付靜態 mockup。
5. 不要把任何 API key 放進前端、提交到 Git，或寫死在程式碼中。
6. AI 回傳內容必須經過 schema 驗證與允許清單檢查；不得讓模型任意輸出可執行 JavaScript、HTML、CSS 或 SQL。
7. 所有修改先進入草稿，業主確認後才發布；提供復原上一版的方式。
8. 免費方案與模型額度可能變動。README 必須標註免費額度、部署與模型能力需在實作當下核實，不承諾永久免費。
9. 不要在第一階段接入 Replit Agent，也不要假設它提供可免費嵌入網站的公開 Agent API。
10. 先閱讀專案，再實作；遇到關鍵技術限制時，記錄選擇與原因，不要默默換成不相容方案。
11. 產品情境
    做一個虛構品牌「CYC Atelier」的形象網站與管理後台，展示業主如何用 Prompt 修改現有網站。
    業主可用 Prompt 完成的修改範例

- 「把首頁主標題改成：讓日常多一點靈感」
- 「整體改成深色、極簡、有高級感的風格」
- 「把主視覺圖片換成更有自然光感的咖啡店照片」
- 「把服務區塊移到品牌介紹前面」
- 「把聯絡我們按鈕改成『預約諮詢』」
- 「把品牌介紹縮短成兩句話」
  Demo 必須真的把使用者的 Prompt 送至 AI 模型，讓模型將自然語言轉成受限制的修改指令；不可用固定關鍵字規則冒充 AI。若 AI 服務尚未設定，畫面需明確顯示「尚未設定 AI」，提供清楚的設定說明，不得假裝成功。

2. 第一階段範圍（MVP）
   A. 公開網站 /
   建立有質感、可供修改的單頁品牌網站，包含：

- Header / 品牌名稱 / 導覽
- Hero：眉標、標題、描述、主按鈕、主視覺圖片
- About：標題、內文、圖片
- Services：可排序的服務卡片
- Contact：標題、描述、按鈕
- Footer
  設計需響應式、可讀性佳、具有清楚的視覺層次。使用合理的示範內容與可替換圖片 URL。圖片載入失敗時需有 fallback。避免依賴不穩定的外部圖片服務才能讓版面成立。
  B. 管理介面 /admin
  左右分欄或其他合理的桌面版配置：
- 左側：Prompt 輸入、提交按鈕、操作狀態、修改摘要、錯誤訊息。
- 右側：網站預覽，或「開啟預覽」入口。
- 顯示「草稿」與「已發布」狀態。
- 顯示目前修改的摘要，讓業主知道哪些欄位將變更。
- 提供「套用到草稿」、「發布修改」、「放棄草稿」等明確操作。
- 可查看最近的修改紀錄；至少保留已發布版本以便復原。
- 手機版仍能操作，不可只做桌面畫面。
  若使用 iframe 預覽，應避免不必要的跨來源限制與安全風險；若架構更適合共用 React 元件直接渲染預覽，優先選擇簡單可靠的方式。
  C. 可由 AI 修改的內容
  只允許修改下列結構化欄位：
- 品牌名稱、導覽文字
- Hero 標題、描述、按鈕文字、按鈕目的地、圖片 URL
- About 標題、內文、圖片 URL
- Services 標題、服務卡片文字與順序
- Contact 標題、描述、按鈕文字
- 受限的主題設定：背景色、文字色、強調色、字體風格選項、圓角風格、版面密度
  主題欄位使用 enum 或允許清單，不接受任意 CSS 字串。URL 僅允許 https:（必要時允許本地 / 路徑），拒絕 javascript:、data: 等危險協定。按鈕連結要驗證格式。
  D. 資料與發布
- 設定明確的 SiteContent / SiteTheme 型別與 schema。
- 至少區分 draft 與 published。
- 業主按發布後，公開網站讀取已發布資料；草稿不應自動覆蓋正式內容。
- 重新整理頁面或重新部署後，儲存的已發布內容應仍存在。
- 開發階段可提供本機 mock repository，但不能把 localStorage 當成正式多使用者資料庫。
- 以 Cloudflare D1 作為首選持久化方案；若目前 repo 的部署模式不支援預期的 D1 綁定方式，先調查並在 README 記錄相容的接法，不要憑空假設。
- 設計 repository/data-access layer，讓本機開發儲存與 D1 可替換。
- 為發布版本保留歷史快照，支援復原最近版本。

3. AI 整合需求
   預期資料流程
1. 前端送出 Prompt。
1. 後端讀取目前草稿內容。
1. 後端把目前可編輯欄位、允許的操作 schema 與 Prompt 傳給 AI。
1. AI 回傳結構化 JSON patch 或修改結果。
1. 後端驗證 JSON schema、欄位白名單、型別、長度、URL 與主題 enum。
1. 驗證成功後，只更新草稿，回傳修改摘要。
1. 前端呈現預覽，業主明確確認後才發布。
   AI 提供者

- 優先評估 Cloudflare Workers AI 的可用模型與目前免費額度。
- 實作前先核實 Cloudflare 官方最新文件：模型是否支援 JSON/structured output、Workers runtime 相容性、需要的 bindings、免費額度與超額行為。
- 若特定模型不支援嚴格結構化輸出，使用一般 JSON 輸出加上伺服器端 schema 驗證與有限重試；不可信任模型輸出。
- 透過 server-side provider adapter 隔離模型廠商，避免 UI 與特定供應商綁死。
- 若需要 API token，使用環境變數或平台 secrets，提供 .env.example（只放變數名稱，不放真實 key）。
- AI 呼叫失敗、超時、超額或輸出不合法時，要顯示可理解的錯誤，不得修改草稿或假裝成功。
- 加入合理的輸入長度限制、請求大小限制與錯誤處理；避免無限重試。
  建議 AI 輸出格式（可依實作調整）
  {
  "summary": "將網站主題調整為深色，並更新主視覺標題",
  "changes": [
  {
  "op": "replace",
  "path": "theme.mode",
  "value": "dark"
  },
  {
  "op": "replace",
  "path": "hero.title",
  "value": "讓日常多一點靈感"
  }
  ]
  }
  要求：
- op 只接受允許的操作。
- path 只能指向允許清單內的欄位。
- value 必須通過該欄位的 schema 驗證。
- 拒絕未知欄位、重複或互相衝突的操作、超長文字及不安全 URL。
- 若需求不在支援範圍，回覆「目前不支援這類修改」與原因；不要擅自修改其他內容。

4. 安全與產品限制

- Demo 可先用單一管理者模式，但在 README 明確說明未完成正式登入、租戶隔離與正式上線所需的存取控制。
- 不可把管理 API 暴露成任何人都能直接修改正式網站的公開端點。
- 若尚未實作身份驗證，部署的 /admin 與寫入 API 應有明確的保護策略；至少不可將未受保護的管理端點當作可公開交付的產品。
- 所有寫入 API 進行 server-side validation。
- 不接受模型提供的程式碼並執行。
- 不允許 AI 修改環境變數、資料庫結構、部署設定、權限或後端程式。
- 記錄必要的修改摘要與時間；不要把 API secrets 或不必要的個資寫進 log。
- 提供「放棄草稿」和「復原上一個已發布版本」。

5. UI / UX 要求

- 簡潔、專業、像真正的 SaaS 工具，不要做成單純聊天機器人 UI。
- 業主不用懂 schema 或程式碼。
- Prompt 例句可供點選填入輸入框，但點選後仍由真正 AI 處理。
- 清楚區分「AI 建議的變更」、「目前草稿」、「正式發布版本」。
- 顯示 loading、成功、驗證錯誤、AI 服務錯誤與儲存錯誤狀態。
- 若 AI 建議多個修改，允許一次預覽整批變更；若實作成本合理，可逐項勾選是否套用。
- 使用鍵盤可操作的表單與按鈕，注意焦點狀態、語意標籤與色彩對比。
- 不要為了動畫而動畫；優先讓編輯、預覽、發布流程清晰。

6. 建議實作順序
   Phase 0 — Repo audit

- 檢查 repo、現有 Next.js/Tailwind 版本、部署設定與既有元件。
- 回報計畫、預期新增/修改檔案與 Cloudflare 相容性風險。
- 不要先大改檔案。
  Phase 1 — 可運作的網站與資料模型
- 建立公開品牌網站。
- 建立共用內容型別、schema、預設內容與主題系統。
- 建立草稿／發布資料流程。
- 先確保不接 AI 時，仍可用表單修改欄位、預覽與發布，驗證整條資料流程。
  Phase 2 — 管理後台 UX
- 建立 /admin。
- 實作 Prompt 輸入、修改摘要、預覽、發布、放棄草稿、歷史版本。
- 用可測試的範例修改流程確認草稿不會直接污染正式網站。
  Phase 3 — 真正的 AI
- 核實 Cloudflare Workers AI 當下可用模型、bindings、免費額度與結構化輸出支援。
- 建立 provider adapter 與 server-side endpoint。
- 串接真實模型、schema validation、錯誤處理與測試。
- AI 未設定時顯示清楚提示；不可悄悄 fallback 成假 AI。
  Phase 4 — 持久化與部署
- 接入 Cloudflare D1 或確認適用的持久化方案。
- 設定本機與 Cloudflare 的環境變數、bindings 與 migration。
- 驗證公開網站讀取 published version、後台讀取 draft、發布後持久保存、版本復原。
- 依目前專案實際 Cloudflare 部署方式設定 build 與部署；不要預設所有 Next.js SSR 功能都能直接用 Pages 靜態匯出實現。
  Phase 5 — 驗收與文件
- 執行 lint、typecheck、tests、build（依 repo 可用指令）。
- 修正錯誤，不可只回報「理論上可用」。
- 更新 README：架構、啟動方式、Cloudflare 設定、AI secrets、D1 migration、部署步驟、免費額度限制、目前未完成的安全功能。

7. 驗收條件

- [ ] 公開網站有完整的示範內容，桌面與手機版皆可用。
- [ ] /admin 可以輸入自然語言 Prompt。
- [ ] Prompt 會送至真正的 AI 模型，不是關鍵字規則模擬。
- [ ] AI 修改結果先進草稿，不會直接改正式網站。
- [ ] 非法 JSON、未知欄位、不安全 URL、任意 CSS/JS 都會被拒絕。
- [ ] 業主能預覽、發布、放棄草稿及復原上一個已發布版本。
- [ ] 發布後公開網站顯示新內容；重新整理後資料仍存在。
- [ ] AI 未設定或超額時，UI 清楚顯示錯誤，不會假裝成功。
- [ ] 沒有 secrets 被提交到 Git 或暴露在瀏覽器。
- [ ] README 的部署步驟依實際專案驗證，而不是猜測。
- [ ] lint、typecheck、tests、build（可用者）通過。
